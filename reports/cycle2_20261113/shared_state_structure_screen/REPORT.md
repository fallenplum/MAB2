# 共享终端图状态：额外费用空间的结构检查

**旧 tune 银行中的端点重合完全由普通共享 anchor 基线解释。** 80 题均是两个不相交的 12 叶星形比较图：24 个边信用对比、26 个终端图状态、关联矩阵秩24。939/1920 个 right 端点也出现在 left 银行中；这939个全部是两个共享基图中心，没有额外跨星形状态共享。

train 的200题中197题结构相同；另外3题的两个星形共享2个叶节点，24状态、24对比、秩23。相对于逐anchor共用中心后的5200个状态，全面去重得到5194个，仅少6个。2347个 right-in-left 单元中2343个为中心，只有4个为非中心。

这些是单seed图状态的结构计数，不能当作实际token、GPU时间或未知质量收益。独立端点基线为每题48状态，而合理共享anchor基线已降到26；把48→26当新方法收益会夸大贡献。跨题复用、实际节点级缓存和反馈评分权限不是此审查的计算对象。

原48.9%左右重合率本身没有错；新的结构证据否定了把它直接解释为额外状态购买空间的建议。原建议及全部负结果保留。这不排除其他图银行结构存在额外共享，也不对所有自适应策略给出无效定理。

协议文件在计算前保存，首次Git发布在结果之后；这是历史结构探索，不能称正式预注册确认。生产脚本只加载partition/left/right索引，不读取quality、原题或新R1。另一实现通过显式关联矩阵秩及节点度数，逐项复算280题全部统计。两次均由root实现，不能称独立外部人工审稿。CPU计时0.0来自本地时钟分辨率，不能解释为没有CPU工作；新增GPU与正式候选轮次均为0。

优势是结论依赖可精确核对的图结构；风险是只覆盖当前旧银行，未构成新模型性能证据。项目保持ACTIVE，当前没有以共享终端状态为由追加GPU的依据。
